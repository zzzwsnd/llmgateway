# LLM Gateway

一个基于 FastAPI 的轻量级 LLM 网关。它为调用方提供统一的旧版 LLM 接口，以及
OpenAI 风格的 Chat Completions 和 Responses 接口；内部按模型枚举、供应商枚举和
上游协议路由请求，并提供模型白名单、受控 Prompt、重试与同协议降级、结构化输出和
调用追踪能力。

## 安装、配置与启动

项目要求 Python 3.14，使用 `uv` 管理锁定依赖。以下命令均使用工作区缓存和锁定的
依赖版本：

```powershell
$env:UV_CACHE_DIR = "$PWD\.uv-cache"
# 单进程开发使用 0；部署时每个并发生成进程必须分配不同的 0..1023 ID。
$env:GATEWAY_SNOWFLAKE_WORKER_ID = "0"
uv sync --dev --locked
uv run --locked uvicorn gateway:app --env-file .env --loop asyncio:SelectorEventLoop --host 0.0.0.0 --port 8000
```

## Docker Compose

Compose 会启动单进程 Gateway、PostgreSQL 17 和 Redis 7.4。首次使用时创建本地环境
文件，并将其中两个密码占位符替换为仅用于当前环境的值：

```powershell
Copy-Item .env.compose.example .env.compose
# 编辑 .env.compose，替换 PostgreSQL 和 Redis 的密码占位符。
docker compose --env-file .env.compose up -d --build --wait
```

供应商 API Key 可以暂时留空；这不影响服务启动和 `GET /v1/models`，但调用对应供应商
前必须在 `.env.compose` 中配置密钥。常用维护命令如下：

```powershell
docker compose --env-file .env.compose ps
docker compose --env-file .env.compose logs -f gateway
docker compose --env-file .env.compose down
```

PostgreSQL 和 Redis 使用命名卷保存数据。只有在明确需要删除本地会话数据时才执行
`docker compose --env-file .env.compose down --volumes`；该操作不可通过重新启动容器恢复数据。

CI 将镜像发布到 `ghcr.io/zzzwsnd/llmgateway`。使用已发布镜像时，在
`.env.compose` 中设置不可变提交标签或版本标签，例如：

```dotenv
GATEWAY_IMAGE=ghcr.io/zzzwsnd/llmgateway:sha-<commit>
GATEWAY_PULL_POLICY=always
```

然后拉取并更新 Gateway，PostgreSQL 和 Redis 的命名卷保持不变：

```powershell
docker compose --env-file .env.compose pull gateway
docker compose --env-file .env.compose up -d --no-build --wait
```

如果 GHCR 包为私有包，需要先执行 `docker login ghcr.io`，所用 Personal Access Token
必须具有 `read:packages` 权限。包的公开或私有状态在 GitHub Packages 设置中管理。

推送到远端默认分支 `main` 后，CI 发布 `latest` 和 `sha-<短提交号>`。创建语义化版本
使用以下命令：

```powershell
git tag v1.2.3
git push origin v1.2.3
```

成功后会发布 `v1.2.3`、`1.2.3`、`1.2` 和 `1` 四个版本标签。当前 Compose 拓扑只运行
一个 Gateway 进程并固定使用 Snowflake worker ID `0`；扩容前必须为每个并发生成进程
分配不同的 `0..1023` worker ID。

## Resumable SSE sessions

Reliable streaming uses a two-step session API. Configure the PostgreSQL and
Redis environment variables named by the top-level `postgres` and `redis` YAML
sections before creating a session. Configure the worker ID named by
`sessions.snowflake_worker_id_env` before starting the application. Hosts,
ports, database names, users, passwords, and API keys must stay in environment
variables; do not put their values in YAML.

Session IDs are `session-{snowflake_id}`, generated by the thread-safe utility
in `app/core/snowflake.py` (41 timestamp bits, 10 worker bits, 12 sequence bits).
Assign a unique integer worker ID from 0 through 1023 to each concurrent
generator process, including processes on the same host. Do not launch multiple
Uvicorn workers with the same worker ID; use one process per deployment replica
and assign different IDs to the replicas. Worker IDs are only for ID uniqueness,
not IP discovery, routing, or service ownership. Clock rollback is rejected.
On first audit or session access in each process, the PostgreSQL adapter checks
and creates or upgrades the `calls` and `call_attempts` tables and their
indexes. Its database role needs DDL privileges for this bootstrap; a
read/write-only application role requires separating schema migrations from
startup in a later deployment change. PostgreSQL must be reachable to create a
session. Redis outages degrade incremental delivery but do not stop generation;
generated text is never persisted in PostgreSQL.

Create a generation independently from its client connection:

```http
POST /v1/stream-sessions
Idempotency-Key: caller-request-1
Content-Type: application/json

{
  "interface": "chat_completions",
  "request": {
    "model": "general-primary",
    "messages": [{"role": "user", "content": "hello"}]
  }
}
```

Then subscribe with `GET /v1/stream-sessions/{session_id}/events`. Reconnect
with the last processed Redis Stream ID in `Last-Event-ID`; delivery is at
least once, so clients must deduplicate by event ID. Active events are replayed
from Redis. When a reachable Redis instance no longer has events for a terminal
call, the subscription returns `410 stream_expired`. Redis unavailability
returns `503 session_runtime_unavailable` and is never treated as expiration.
The server does not automatically repeat an expired call because it does not
persist replayable request content. Redis operation deadlines prevent stalled
reads/writes from blocking generation or cancellation indefinitely.
Malformed or implausibly future `Last-Event-ID` values are rejected because a
future cursor would hide subsequently appended data and control events.
Each Redis event write also sets a fallback expiration of at least 24 hours;
normal terminal cleanup shortens it to the configured replay TTL. Once the
Stream expires, clients submit the original request again with a new
`Idempotency-Key` and `retry_of_call_id`. The gateway validates owner,
interface, and request fingerprint before creating the linked new call.

The other session operations are:

| Endpoint | Meaning |
| --- | --- |
| `GET /v1/stream-sessions/{session_id}` | Read durable execution status and public runtime health. |
| `DELETE /v1/stream-sessions/{session_id}/connections/{connection_id}` | Detach one physical client SSE connection. Generation continues. |
| `POST /v1/stream-sessions/{session_id}/cancel` | Cancel model generation and invoke the compensation hook. |

Multiple physical subscriptions are allowed for one session. Closing a page,
losing the network, or calling the detach endpoint never cancels the provider
request. The first version keeps the provider task on its creating process; if
that process exits, reconciliation marks the session failed and does not repeat
the billed model call on another node.

PostgreSQL stores call state, activity timestamps, and content-free attempt
audit metadata. Call rows do not persist CAS, generation, or execution-fencing
tokens; state transitions use database transactions, row locks, and legal
transition checks. Redis stores one content Stream per session:

```text
provider connection -> XADD gateway:session:{session_id}:events
                     -> XREAD with an independent cursor -> client SSE connection
```

There are no node/IP records, producer leases, connection locations, or separate
cancellation keys. Subscribers use independent `XREAD` cursors, not consumer
groups, so every subscriber receives the same events. `control.cancel` and
connection-specific `control.detach` use the same Stream and are never exposed
as public SSE events. A connection ID is ephemeral and exists only in the
subscriber iterator. Status reports `active_connections: null` and
`producer_health: "unknown"`; physical connection counts are not tracked.
Each subscriber initializes a separate control cursor at the Stream tail, so a
client replay cursor can never hide a later connection-specific detach event.

The generation and subscription roles can run on different processes or
services: SSE subscription needs only the session Stream and durable session
record, never the producer address. This version still admits generation through
the create endpoint and its local supervisor; it does not add a separate job
queue or deployment entrypoint. Live and queued sessions refresh PostgreSQL
activity timestamps. Reconciliation only closes stale sessions; it never
restarts a provider request. A failed control-event write returns a sanitized
runtime error, while the durable cancellation state remains authoritative.

Existing one-step streaming endpoints remain compatible but do not
provide the durable reconnect contract of `/v1/stream-sessions`.

The durable audit model has exactly two business dimensions. `calls` stores one
client-visible logical invocation and its current/final state. `call_attempts`
stores one row per physical upstream request with type `initial`, `retry`,
`fallback`, or `json_retry`. Token usage, cost, attempt count, and final model
are aggregated from attempts. Local JSON bracket repair updates the producing
attempt and does not create another attempt. Neither table stores request text,
response text, prompt bodies, JSON Schemas, credentials, provider model names,
base URLs, or raw provider errors.

运行时配置来自 YAML，解析顺序固定如下：

1. 已设置时使用 `GATEWAY_CONFIG_FILE` 指向的文件。
2. 否则使用存在的本地文件 `config/gateway.yaml`。
3. 最后回退到已提交的开发示例 `config/gateway.example.yaml`。

可从示例创建本地 `config/gateway.yaml`，但不要提交它。YAML 的供应商项只保存
`api_key_env`，即 API Key 所在环境变量的名称，绝不保存原始密钥。例如，当前示例中
DeepSeek 使用 `DEEPSEEK_API_KEY`，OpenAI 使用 `OPENAI_API_KEY`。密钥在首次调用该
供应商时才读取，因此未配置密钥不影响启动或 `GET /v1/models`；实际调用会返回
`gateway_misconfigured`，且响应和日志不会暴露密钥或环境变量的值。

`app/core/config.py` 是可执行的配置基础设施：它负责路径选择、YAML 加载、Pydantic
校验、结果缓存和延迟密钥读取。应用、重试、模型和供应商数据并不定义为其中的模块常量，
而是由 `app/model/config.py` 中的配置实体承载。

## 分层架构

```text
gateway.py                  兼容启动入口，仅导出 app.main:app
app/
  main.py                   唯一的组合根，负责跨层对象装配
  controller/               HTTP 路由、请求/响应边界、SSE 响应包装
  service/                  业务编排、工厂、重试、降级、协议校验与响应呈现
  dao/                      薄协议/数据调用包装
  mapper/                   SDK 与存储访问、异常转换、供应商响应提取
  model/                    请求、响应、DTO、实体、枚举和配置实体
  core/                     配置工具、全局错误处理、日志和无状态工具
config/
  gateway.example.yaml      已提交的开发配置示例
tests/                      单元、API、配置和架构测试
```

业务依赖方向必须严格保持为：

```text
controller -> service -> dao -> mapper
```

各层可以依赖 `model` 和不包含业务逻辑的 `core`。只有 `app/main.py` 可以跨层构造对象；
不得跳过中间层、反向导入，或通过间接导入规避边界。架构测试会递归扫描每一层的全部
Python 文件，包括 `app/service/provider/` 下的供应商实现。

## 模型、供应商与协议路由

对外可用的标识符全部由代码枚举定义：`ModelEnum`、`ModelProviderEnum` 与
`LLMProtocolEnum`。HTTP 请求的 `model` 字段和 YAML 的模型/供应商映射键都必须是有效
枚举值；任意字符串不能在运行时变成新的模型或供应商。

服务层有两个相互独立的工厂：

```text
ModelEnum -> 模型路由配置 -> ModelProviderEnum
                              -> ProviderFactory
                              -> dict[ModelProviderEnum, ModelProvider]

模型路由配置中的 LLMProtocolEnum
                              -> ProtocolFactory
                              -> dict[LLMProtocolEnum, ProviderDao]
```

`ProviderFactory` 选择由供应商枚举注册的实现，`ProtocolFactory` 选择与上游协议对应的
DAO。新增供应商时，应增加供应商枚举、YAML 供应商配置、`app/service/provider/` 下的
`ModelProvider` 实现，并在 `app/main.py` 的供应商映射中注册。新增协议时，应增加协议
枚举、独立 mapper 和薄 `ProviderDao`，再在 `ProtocolFactory` 的协议映射中注册。模型
路由与协议路由不能合并为一个枚举或一个工厂。

### 严格协议匹配

原生接口绝不进行协议桥接：

```text
POST /v1/chat/completions -> CHAT_COMPLETIONS 上游模型
POST /v1/responses        -> RESPONSES 上游模型
```

Chat Completions 请求不能翻译为上游 Responses 请求，Responses 请求也不能翻译为上游
Chat Completions 请求。任何不匹配都会在供应商调用之前返回 `protocol_mismatch`。降级
模型必须与原模型使用相同的上游协议，配置校验会拒绝跨协议降级。旧版 `/v1/llm` 接口
保持协议中立，按所选模型的 YAML 上游协议执行。

### 模型重试、fallback 与 JSON 纠错重试

重试参数由 YAML 顶层的 `retry` 配置统一控制：

| 配置项 | 含义 |
| --- | --- |
| `max_retries_per_model` | 每个模型在首次调用之后允许的最大重试次数；因此单个模型最多调用 `1 + max_retries_per_model` 次。 |
| `initial_delay_seconds` | 第一次重试前的等待时间。 |
| `backoff_multiplier` | 后续等待时间的指数退避倍数。第 `n` 次重试前等待 `initial_delay_seconds * backoff_multiplier^n` 秒，其中 `n` 从 `0` 开始。 |

`attempts` 统计一次请求实际发起的全部上游调用，包括供应商故障重试、JSON 纠错重试和
fallback 调用。每个 fallback 模型重新获得一份完整的单模型重试预算，但同一模型内的供应商
故障重试和 JSON 纠错重试共用该预算，并不是两个独立计数器。OpenAI SDK 自带重试已关闭，
以确保重试次数和退避时间只由网关控制。

非流式请求按以下顺序处理：

1. 调用请求指定的主模型。连接失败、超时、限流以及 Responses 的 `failed` / `incomplete`
   终态会转换为可重试错误，在当前模型上按指数退避重试。
2. 当前模型的重试预算耗尽后，按各模型 YAML 中的 `fallback` 继续尝试。fallback 可以形成
   多级链，但每个候选模型仍需通过协议和能力校验，且必须与原模型使用相同的上游协议。
3. 非可重试的普通上游异常不会在当前模型上重试，而是直接进入下一个 fallback。请求及
   主模型校验错误、供应商返回的网关业务错误直接返回，不会通过切换模型掩盖。
4. 所有候选模型都失败时返回 `model_unavailable`。结构化输出已经获得响应、但最终 JSON
   仍不合法时属于输出校验失败，按下述 JSON 策略返回错误，不进入 fallback。

流式请求还受“内容是否已经公开给客户端”约束：

- 首个非空 delta 产生前，可重试错误可以在当前模型重试；预算耗尽后可以进入 fallback。
- 已输出 delta 后，只有供应商同时给出可恢复的 `resume_token` 才能继续重试当前模型。恢复
  游标只属于当前上游模型；进入 fallback 时会清空，不会传给备用模型。
- 已输出 delta 后若没有可恢复游标，或恢复重试最终耗尽，网关返回
  `upstream_stream_failed`，不会切换 fallback，以免把两个模型的文本拼接成一个响应。
- 非可重试的流式异常会立即结束本次生成，不重试也不进入 fallback。

JSON 纠错只适用于带 `response_schema` 的非流式结构化输出请求，处理顺序如下：

1. 在调用任何供应商之前校验 JSON Schema；Schema 自身非法时返回
   `invalid_response_schema`，不发起上游调用。
2. 对模型文本执行标准 JSON 解析。若仅缺少末尾的 `}` 或 `]`，网关会先在本地补齐并重新
   解析；补齐后同时通过 Schema 校验即可直接成功，不消耗额外上游调用。
3. 无法本地修复时返回内部的 `invalid_json` 诊断；能解析但不符合 Schema 时生成
   `schema_validation_failed` 诊断，其中包含缺失字段和错误字段的 JSON 路径。
4. 当前模型仍有重试预算时，网关使用“原始消息 + 本次失败的 assistant 输出（非空时）+
   JSON 纠错 user 提示词”重新调用同一模型。纠错提示词来自
   `json_parsing.retry_prompt.active_version` 指向的版本，并注入失败诊断与完整 Schema。
5. 纠错预算耗尽后分别返回 `invalid_json` 或 `schema_validation_failed`，不进入 fallback。

JSON 纠错调用仍携带原始结构化输出要求。所有已成功返回到网关的上游 completion 用量都会
累加到最终成功响应的用量中，因此失败输出和纠错输出产生的 token 也计入总用量。

## API

当前公开以下端点：

| 端点 | 说明 |
| --- | --- |
| `POST /v1/llm` | 旧版统一的非流式 LLM 调用。 |
| `POST /v1/llm/stream` | 旧版统一的 SSE 流式调用。 |
| `POST /v1/chat/completions` | 支持文本子集的原生 Chat Completions 调用或 SSE 流。 |
| `POST /v1/responses` | 支持文本子集的原生 Responses 调用或 SSE 流。 |
| `GET /v1/models` | OpenAI 风格的可用模型列表和能力元数据。 |
| `GET /v1/traces` | 当前进程中的调用追踪元数据。 |
| `POST /v1/stream-sessions` | 创建独立于客户端连接的生成会话。 |
| `GET /v1/stream-sessions/{session_id}` | 查询持久化会话状态和最终文本。 |
| `GET /v1/stream-sessions/{session_id}/events` | 从会话 Stream 订阅或重放 SSE。 |
| `DELETE /v1/stream-sessions/{session_id}/connections/{connection_id}` | 仅断开指定订阅连接。 |
| `POST /v1/stream-sessions/{session_id}/cancel` | 取消生成并调用补偿服务。 |

### 旧版 LLM 接口

非流式请求示例：

```json
{
  "model": "general-primary",
  "messages": [{"role": "user", "content": "你好"}],
  "timeout_seconds": 30
}
```

向 `POST /v1/llm/stream` 提交相同请求并设置 `"stream": true` 可获得
`text/event-stream`。旧版流事件包括 `content.delta`、`response.completed` 和
`response.failed`。旧版非流式请求可通过 `response_schema`（以及可选的
`response_schema_name`）要求 JSON Schema 结构化输出；流式请求不能同时使用
`response_schema`。

### 原生 Chat Completions 与 Responses

Chat Completions 的最小文本请求：

```json
{
  "model": "general-primary",
  "messages": [{"role": "user", "content": "请用一句话介绍网关"}]
}
```

设置 `"stream": true` 后，Chat 流依次输出 `chat.completion.chunk` 事件、最终的 stop
chunk 和 `[DONE]`。Chat 的结构化输出使用 `response_format`，支持 `json_schema` 与
`json_object` 两种格式；结构化输出不能与 `stream: true` 同时使用。

Responses 的最小文本请求：

```json
{
  "model": "general-responses",
  "input": "请用一句话介绍网关"
}
```

`input` 也可以是带 `system`、`user` 或 `assistant` 角色的文本消息列表。设置
`"stream": true` 后，Responses 流包含 `response.created`、
`response.output_text.delta`、`response.output_text.done` 和 `response.completed` 等文本
生命周期事件。Responses 的结构化输出通过 `text.format` 指定，支持 `json_schema` 与
`json_object`；结构化输出不能与 `stream: true` 同时使用。

`GET /v1/models` 返回模型枚举、所属供应商、协议和能力标记，不返回 API Key、base URL、
供应商模型名、价格或降级映射。`GET /v1/traces` 返回模型、Prompt 版本、token、成本、
延迟、尝试次数和状态等当前进程元数据，默认不保存对话正文。

## 当前能力与范围

当前支持的原生协议子集为：文本输入与文本输出、JSON 结构化输出、非流式调用和流式
调用。流式和非流式均经过模型白名单、供应商/协议工厂、重试和同协议降级路径。

已具备的功能包括：

- 异步旧版 LLM 和 SSE 流式调用。
- OpenAI Compatible 的 Chat Completions 与 Responses 上游适配。
- 枚举模型别名、模型白名单和 `GET /v1/models` 能力发现。
- 主模型的临时故障重试，以及 YAML 定义的同协议备用模型降级。
- 受控 Prompt 模板、版本选择和变量渲染。
- JSON 结构化输出请求、解析和 JSON Schema 校验。
- token、成本、延迟、尝试次数和状态追踪。
- 可恢复 SSE 生成会话：客户端断开后继续生成，支持增量重放和最终结果快照。
- Pydantic 请求/响应约束、统一 `GatewayError` 转换，以及不暴露供应商密钥的错误处理。

当前不支持工具或函数调用、图像/音频等多模态输入输出、后台 Responses 任务、
通用对话上下文会话，也不支持任何跨协议转换。原生请求模型使用严格字段校验，
未支持的字段会被拒绝。

## 工程能力

- FastAPI 异步接口和应用工厂，且保留 `gateway:app` 兼容启动入口。
- 六层依赖边界及递归 AST 架构测试。
- 枚举键控的 ProviderFactory、独立的 ProtocolFactory，以及构造函数注入。
- Service 不直接导入供应商 SDK；SDK 调用和响应提取仅在 Mapper 层。
- Pydantic YAML 配置校验、枚举校验、供应商协议校验和同协议降级校验。
- 锁定依赖的测试、编译和启动流程。

## 当前限制与后续存储路线

调用审计和流式状态已经持久化到 PostgreSQL 的 `calls`、`call_attempts`；Prompt、模型配置
和价格仍保存在进程内。流式供应商响应目前没有 token 用量，因此对应 attempt 的 token 和
成本可能为零。`GET /v1/traces` 从 PostgreSQL 聚合读取，但暂不提供分页或清理策略；项目也
尚未提供认证、租户隔离、限流、健康检查、指标或分布式追踪。

Redis Stream 是生成文本增量和终态事件的唯一存储。事件过期后不能从 PostgreSQL 恢复正文，
客户端必须按 `410 stream_expired` 契约重新提交并关联旧调用。后续扩展 Prompt、模型和价格
持久化时，实现必须落在 Mapper 层，并保持 DAO 方法契约不变。
